# 04 藍牙音樂

目前的研究優先項目。分成三條路：Pi 中繼（已成功）、Android 手機 App（已編譯）、原機直接 A2DP（研究中）。

## 1. Pi 中繼（實機成功）

原機只開放 HFP 通話音訊，所以讓 Pi 扮演「手機」：

```
手機 ──A2DP/SBC 44.1kHz 立體聲──▶ Pi (BlueALSA) ──FFmpeg──▶ HFP SCO 8kHz 單聲道 ──▶ Garmin 喇叭
```

關鍵步驟：

1. Pi 先提供 HFP Audio Gateway，再把藍牙裝置類型設成「手機」，Garmin 才找得到並配對（名稱 `Garmin-Pi`）。
2. `scripts/nuvi_pairing_agent.py` 只接受已識別的 nüvi，處理確認與固定 PIN 1234。
3. 透過 RFCOMM 送 `+CIEV: 2,1` 模擬通話中，再用 BlueALSA 的 SCO PCM 播放。直接送 PCM 曾經無聲。
4. BlueALSA v4.3.1 的 CIND 查詢固定回覆閒置狀態，會和模擬通話矛盾；已做來源修正版並通過 RFCOMM 測試。

實測：使用者確認持續聽到手機音樂 60 秒。限制是電話畫面、8 kHz 單聲道音質、長時間穩定度未測。

常用指令：

```sh
python3 scripts/test_hfp_call_audio.py --repeat 1                     # 播放測試旋律
python3 scripts/test_hfp_call_audio.py --wav /path/to.wav --repeat 1  # 播放指定 WAV
python3 scripts/garmin_phone_audio_bridge.py --max-seconds 300 --volume 0.7 --live-cind-test
python3 scripts/garmin_music_player.py --plan-conversion song.mp3     # 只看轉換計畫
```

後續強化（離線驗證）：

- `scripts/garmin_host_audio_pipeline.py`：監督整條管線，任一段失敗都會回收所有子程序。
- `scripts/garmin_pcm_meter.py`、`scripts/garmin_audio_volume_observer.py`：可選的音量與 RMS 數值紀錄，不存音訊。
- 固定增益轉換，沒有 AGC；反相左右聲道在預設混音會互相抵消，可選單一聲道。
- HFP 協商仍是 CVSD，Garmin 端沒有宣告 mSBC；音量起伏的原因未證實。

## 2. Android HFP App

見 [07 Android HFP App](07-Android-HFP-App.md)。目標是省掉 Pi：手機自己建立本機來電，把音檔送到 Garmin 通話輸出。尚未實機測試。

## 3. 原機直接 A2DP（研究中）

目標：手機直接配對 Garmin 播音樂，並在原機菜單加入播放器。需要的元件與進度：

| 元件 | 狀態（離線模擬） |
| --- | --- |
| 自製 SEP 端點註冊、SDP Audio Sink 公告 | 在原廠 SDP／AVDTP 程式上跑通 |
| Configure／Open／Start／Suspend 的原生處理與保護 | 跑通，並修正數個原廠邊界問題（如未支援指令回覆格式） |
| 收到媒體封包 → SBC 解碼 → 轉 16 kHz 單聲道 | 與上游 libsbc 逐 byte 相同 |
| 接入原廠音源佇列、混音器、計時器 | 在原廠 OS20 核心排程下跑通，含暫停／恢復與停止回收 |
| 菜單入口「Pi 播放器」、字型與圖示繪製 | 原廠格位、字型、繪圖流程畫出到模擬畫布 |

尚未完成：真正的資源所有權保證、完整 STOP_DONE、安全卸載、多工下與導航語音共存、實機喇叭、可安裝的套件。
這部分程式在 `native/`，說明見 [05 原生程式與 GarminOS](05-原生程式與GarminOS.md)。

已取消的項目：手機麥克風遠端擴音、聲道與音質精修。
